# m3kit (Angular Reporting Reference) Constitution

## Core Principles

### I. Clean-Room Integrity (NON-NEGOTIABLE)

This project is a public, independently authored, clean-room reference. Nothing in it
may derive from any private or proprietary source.

- Prohibited inputs: private code, API shapes, ticket content, screenshots,
  terminology, business workflows, data, design assets, or confidential architecture
  may never be consulted, referenced, paraphrased, or reproduced — directly or from
  memory of specifics.
- Permitted inputs: public sources only — angular.dev (and versioned v19 docs),
  material.angular.dev / material.angular.io, ngrx.io (Signals / SignalStore), and
  nx.dev — plus apache.org/licenses, the npm public registry, and Node.js release docs
  for licensing/tooling mechanics, plus any other explicitly public, citable source
  provided it is logged in `docs/BOUNDARY_LOG.md` at the time of consultation. Generic,
  industry-common enterprise reporting patterns (tables, filters, sorting, pagination,
  export concepts) are permitted as public knowledge.
- No real data, ever: no production-like datasets, no scraped data, no PII-shaped real
  values. All data is fabricated by factories/fixtures in `libs/reporting/testing` or
  static JSON authored for this repository.
- Doubt resolves to exclusion: if there is any uncertainty whether something is generic
  public knowledge versus privately derived, it is excluded until cleared at a review
  gate.

### II. Source-Internalization First

The adoption model is: reference repo → consumer performs a source import / internal
fork → internal ownership transfer. This is not an npm package and never becomes one.

- Copy-in-ability beats abstraction: prefer plain, readable, conventional code that a
  team can lift into their monorepo and immediately own, over clever indirection or
  configurability aimed at hypothetical reuse.
- Minimal external dependencies: only the pinned stack (Principle III) plus what Nx
  generates by default. Every additional dependency requires justification in
  `docs/DECISIONS.md`.
- No exotic build steps: standard Nx/Angular esbuild pipeline only. No custom
  compilers, code generation steps, or postinstall machinery.
- Self-contained libs, conventional layout: libraries follow standard Nx layout and
  remain individually liftable; nothing depends on repo-global magic.
- Internalization is documented: `docs/INTERNALIZATION_GUIDE.md` and
  `docs/ADOPTION_GUIDE.md` are first-class deliverables, kept current with the code.

### III. Pinned-Stack Discipline

The stack is pinned by explicit decision. "Latest" is not a reason to change anything.

- Pinned versions: Angular 19 (19.2.x line), Angular Material 19 + CDK 19,
  `@ngrx/signals` 19.x, Nx 20.x (the Nx major supporting Angular 19), TypeScript
  `>=5.5 <5.9` (Angular 19.2's supported range), esbuild application builder, ESLint
  flat config as generated by Nx, Jest via Nx defaults. License: Apache-2.0.
- No drive-by major upgrades: no upgrading Angular, Nx, Material, NgRx, or TypeScript
  majors/minors outside the pinned lines without an explicit recorded decision.
  Tooling that "wants" newer versions is constrained, not obeyed.
- Patch updates within the pinned lines are permitted when needed for builds to pass,
  and noted in `docs/DECISIONS.md` if non-trivial.

### IV. Phasing and Review Gates

Work proceeds in declared phases; gates are not skippable.

- Phase order: (1) scaffold-only → (2) clean-room compliance review gate → (3) core
  reporting contracts/query behavior → (4) Material reporting shell → (5) synthetic
  invoice demo route → (6) final clean-room review.
- Scaffold-before-features: during the scaffold phase only workspace, libs, docs, and
  module boundaries with minimal placeholder code are permitted. Build, lint, and test
  must be green. Full features are forbidden in this phase, even if easy.
- Review gates block expansion: no feature-phase work begins until the clean-room
  compliance review gate passes. The final clean-room review precedes any public
  promotion of the repository as complete.

### V. Synthetic Data Only

- All runtime, demo, test, and documentation data is synthetic, in-memory or static
  JSON, generated within this repository.
- Approved synthetic domains only: customers, orders, invoices, support tickets,
  products. No other domain vocabulary may appear in code, docs, tests, or fixtures.
- No auth, no backends, no network data sources in the reference. Datasource
  *interfaces* may model asynchrony, but shipped implementations are in-memory/static.
- Fixtures and factories live in `libs/reporting/testing` and use only the approved
  synthetic domains.

### VI. Boundary-Log Duties

- Whenever an external pattern, doc page, or public reference is consulted to make a
  design or implementation choice, an entry is added to `docs/BOUNDARY_LOG.md` at the
  time of consultation — never retroactively — recording what was consulted, why, and
  what was taken from it. This is the audit trail proving clean-room provenance.
- `docs/CLEAN_ROOM.md` states the clean-room policy and permitted sources; it is kept
  authoritative and current.
- `docs/DECISIONS.md` records every consequential decision: dependency additions,
  version changes, architectural choices, constitutional amendments.
- Docs are updated in the same change that makes them stale; "docs later" is a
  violation.

### VII. Simplicity Bias

- No speculative abstraction: build only what the current phase's spec requires. No
  plugin systems, no generic frameworks-within-the-framework, no configuration
  surfaces without a present consumer.
- State management restraint: `@ngrx/signals` (SignalStore) only where state
  complexity justifies it; plain Angular signals/inputs otherwise. No additional state
  libraries, ever, without a recorded decision.
- Boundaries over cleverness: architecture is enforced by Nx module boundary tags —
  `material → core` allowed, `testing → core` allowed, `core` depends on nothing
  internal, the app may depend on all libs. Code that fights the boundaries is wrong
  by definition.
- Readable over impressive: the reference exists to be read, evaluated, and copied by
  enterprise teams. Optimize for comprehension.

## Technology Constraints

The workspace is an Nx 20 Angular monorepo: one demo application
(`apps/demo-reporting`) and three libraries (`libs/reporting/core`,
`libs/reporting/material`, `libs/reporting/testing`). Version pinning uses tilde
ranges for framework packages (`~19.2.0` style, never `^` drifting across minors for
Angular itself), and the lockfile is committed as part of the reference so that
consumers who source-internalize can reproduce the build. Libraries are
non-publishable; there is no release pipeline, no semantic-release, no changesets.
E2E testing is deliberately deferred beyond the scaffold phase.

## Development Workflow and Quality Gates

- `nx run-many -t lint test build` must pass for all projects at the end of every
  phase; this command is the contract any future CI wraps.
- Module-boundary rules are lint-enforced; a deliberate violation must fail lint, and
  that verification is recorded in `docs/BOUNDARY_LOG.md`.
- Every review gate (Principle IV) includes an explicit constitution-compliance check;
  any violation blocks the gate until remediated.
- Commit history stays clean: personal author identity, no internal identifiers,
  ticket IDs, or planning-tool references in code, docs, commit messages, or branch
  names.

## Governance

- This constitution supersedes all other practices and applies to all contributors,
  agents, and phases of the project. Every spec, plan, task, and code change MUST
  comply; where a principle conflicts with convenience, the principle wins.
- Principle I (Clean-Room Integrity) cannot be amended, only tightened.
- Other amendments require an explicit entry in `docs/DECISIONS.md` describing the
  change and rationale.
- All PRs and reviews must verify compliance; complexity beyond what the current
  phase's spec requires must be justified or removed.
