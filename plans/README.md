## Why this sequence

1. Plan 001 tightens the generated runbook/quickstart/prompt contract before more agents rely on it. The current generated customers packet is intentionally safe but too thin for a lower-level executor: `m3kit-porting/customers/customers-report/runbook.md:3-22`, `quickstart.md:3-9`, and `ai-wiring-prompt.md:1-3` omit route-match verification, side-by-side comparison steps, expected results, and `NX_DAEMON=false` guidance.
2. Plan 002 then extends target resolution. The product spec says route path and project+page are valid targets (`specs/007-app-porting-skill-generators/spec.md:42`), but `port-analyze` currently normalizes `options.target` and immediately requires `tree.exists(target)` (`tools/plugin/src/generators/port-analyze/generator.ts:32-35`).
3. Plan 003 is the highest-leverage UI direction item. The tournament evidence says Data Table Column Manager won because `m3k-data-table` already accepts `columnState` and core already resolves headless column state (`docs/readiness/m3kit-ui-tournament/2026-07-06/video-package/voiceover-script.md:21-25`).
4. Plan 004 follows the app-porting hardening work by making generated consumer libs easier to lint correctly. Generated `customers-*` projects carry `scope:customers` + type tags (`libs/customers/ui/project.json:6-9`), while the root boundary config only constrains `scope:m3kit-*` and `type:app` (`eslint.config.mjs:30-118`).

## Findings considered and selected

### P1 selected — App-port runbooks are safe but not executor-complete
- Category: DX/docs
- Evidence: `docs/APP_PORTING.md:52-64` promises manual wiring, tests, comparison, and rollback; generated example `m3kit-porting/customers/customers-report/runbook.md:3-22` includes lift, route snippet, and rollback only. `quickstart.md:3-9` lists tests but not expected results or daemon/cache policy. `ai-wiring-prompt.md:1-3` is a single paragraph, not a scoped execution packet.
- Impact: smaller agents can wire routes or run tests without first proving they are operating on the intended route/project; failures become ambiguous and harder to review.
- Effort: M. Risk: LOW. Confidence: HIGH.
- Plan: `001-harden-app-port-runbooks.md`.

### P1 selected — `port-analyze` does not yet support route/project+page targets promised by the spec
- Category: correctness/DX
- Evidence: `specs/007-app-porting-skill-generators/spec.md:42` accepts target component path, route path, or project+page; implementation throws unless the normalized `target` path exists (`tools/plugin/src/generators/port-analyze/generator.ts:32-35`). Route snippets are discovered after a component target exists (`generator.ts:135-162`).
- Impact: users must know the exact component file path before analysis, which undercuts analyzer-first migration from a route or page name.
- Effort: M. Risk: MED. Confidence: HIGH.
- Plan: `002-support-route-target-analysis.md`.

### P1 selected — Data Table Column Manager has unusually high leverage
- Category: direction
- Evidence: tournament recommendation: `docs/readiness/m3kit-ui-tournament/2026-07-06/video-package/voiceover-script.md:21-25`; headless model: `libs/core/src/lib/column-state.ts:4-10`, `:55-88`; table input: `libs/table/src/lib/data-table.component.ts:110-112`, `:228-232`; demo already stores column state for saved views/exports (`apps/demo-reporting/src/app/reports/reports.component.ts:104-113`, `:151-158`).
- Impact: closes a visible enterprise reporting gap using existing contracts, enabling users to modify column visibility/order/pinning before saved views persist that state.
- Effort: L. Risk: MED. Confidence: HIGH.
- Plan: `003-column-manager-spec-pack.md`.

### P2 selected — Generated consumer libs need boundary guidance
- Category: DX/tooling
- Evidence: generated projects have tags (`libs/customers/feature-customers-report/project.json:6-9`, `libs/customers/data-access/project.json:6-9`, `libs/customers/ui/project.json:6-9`) but no generated or printed `depConstraints`; root `eslint.config.mjs:30-118` only defines the m3kit library graph and `type:app` allowance.
- Impact: the scaffold looks Nx-shaped but does not give consumers a clear way to enforce `feature -> data-access/ui`, `ui -> m3kit only`, and `data-access -> no UI` constraints.
- Effort: M. Risk: LOW. Confidence: MED-HIGH.
- Plan: `004-consumer-boundary-guidance.md`.
